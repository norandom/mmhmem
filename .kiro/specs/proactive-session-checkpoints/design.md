# Technical Design

## Overview

Make checkpointing part of normal agent work, then present the exact recovery
boundary after interruption. Keep existing MCP tool arguments, transports,
project keys, storage tables, and installer destinations.

### Goals

- Guide agents to save the initial objective, milestones, and changed final responses.
- Recover the latest saved checkpoint with its timestamp and available activity.
- Preserve the previous checkpoint when a replacement fails before commit.

### Non-Goals

No signal hooks, native `/clear` interception, background autosave, transcript
import, project-key normalization, or guarantee that an interrupted agent
had time to save its latest action. No new worker, library, or service.

## Boundary Commitments

### This Spec Owns

- Checkpoint trigger instructions in MCP server guidance, the canonical skill,
  its generated package, and existing recap commands.
- Session checkpoint transaction completion, resume metadata, and recovery text.
- Tests and user documentation for these contracts.

### Out of Boundary

Harness event handling, chat databases, filesystem scanning, schema changes,
installer selection/configuration UI, worker setup, shunting, and global
reconciliation between audit files and database commits.

### Allowed Dependencies

Existing SessionBus, Db connection closure, synchronous AuditWriter, SQLite
transactions, `time` formatting, MCP result types, and marketplace builders.
Dependencies remain MCP -> services -> storage. Guidance remains an agent
instruction contract, not a background execution component.

### Revalidation Triggers

Changes to checkpoint arguments, timestamp semantics, task-ID response text,
project keys, audit ordering, the 200-token playbook estimate, packaged-skill
parity, or command installation destinations require integration revalidation.

## Architecture

The agent initiates saves through the existing checkpoint operation. SessionBus
owns persistence and acknowledgement; MCP owns presentation. Recap commands
request recovery and faithfully explain its result. No new lifecycle service
is introduced.

1. Resume using the same exact project key throughout a task.
2. If no checkpoint exists, save the accepted objective and next step.
3. Save changed state after a task unit, validation batch, plan-changing
   decision, or new blocker; save before yielding a final response if still dirty.
4. Before an agent-controlled clear or handoff, save changed state and await
   acknowledgement. Ctrl+C/native clear does not trigger an assumed save.
5. On recovery, display the checkpoint, recorded activity, or explicit absence.

## Components and Interfaces

### Checkpoint service

Extend the internal `ResumeView` with
`checkpoint_saved_at_epoch: Option<i64>`, selecting the existing
`active_sessions.updated_at_epoch`. `Some` means a stored checkpoint;
`None` means no checkpoint. Add `saved_at_epoch: i64` to `CheckpointAck`,
using the same captured timestamp as the database row and checkpoint breadcrumb.
These structs are internal; the MCP argument schema and tool count stay unchanged.

Use one database transaction inside the existing connection closure for the
active-session upsert and `session_handoff` breadcrumb insertion. Emit the
existing checkpoint audit event before committing; audit failure rolls back
both database writes. Return acknowledgement only after commit. This avoids
holding a database transaction across asynchronous operations. AuditWriter
must not call back into Db, preserving a one-way lock order.

An audit append may survive a subsequent database commit failure. The audit
line records a checkpoint attempt, not a receipt; the committed database row
and successful tool reply are authoritative for recovery. Document that limit
in the service contract; do not invent cross-resource atomicity. If commit
succeeds but the transport loses the reply, recovery may reveal the newer
persisted checkpoint: unacknowledged does not necessarily mean uncommitted.
Optional client-usage recording remains best effort after the save, as today.

The resume operation continues to load history before appending its own resume
breadcrumb. Its generated task ID does not create an active-session row.

### Recovery presentation

Provide private pure functions that accept `ResumeView` or `CheckpointAck`
plus the project name and return Markdown strings. Keep `worker_notice()`
appending in the MCP layer for every resume case.

- **Checkpoint present:** show saved state, objective, task, last harness,
  and UTC save time with epoch milliseconds. Show recent breadcrumbs in a
  separate recorded-activity section, each with its own timestamp.
- **No checkpoint, history present:** state that no working-state checkpoint
  was saved, show the available breadcrumbs, and explain how the original
  harness conversation can be used to create one.
- **Neither present:** report no checkpoint and no recorded prior activity.
  Show the initialized task ID without implying a save occurred.

Preserve recognizable `Checkpoint saved`, `No active cross-agent session`,
and `Initialized new task ID` phrases where compatible. Put the task ID on
its own predictable line; tests extracting it must stop at that line and
trim terminal punctuation instead of consuming the rest of the response.
Tied timestamps do not establish order. A `session_handoff` breadcrumb is a
save event, not later unsaved user work. If time formatting fails, show the
raw epoch value rather than failing recovery.

### Agent and recap guidance

Maintain an agent-local distinction between current working state and the
last acknowledged checkpoint. An acknowledgement clears the dirty state;
a failed attempt does not. Meaningful state is objective, completed work,
decisions, blockers, and next steps, not a raw transcript. No persistent
scheduler or dirty-state database is added.

Canonical guidance states the trigger rules compactly; server instructions
reinforce them. Recap templates stop suppressing the no-checkpoint response
and present available history with the appropriate limitation. Guidance is
best effort because an agent can ignore instructions; static checks cannot
prove universal model compliance.

## Data Models

No schema migration or new table. Checkpoint timestamps and breadcrumb times
already exist. Project and task keys, redaction, and the existing state-size
budget remain unchanged. Read-only recovery does not synthesize checkpoint
content from breadcrumbs or import harness chats.

## Error Handling

- Database or audit failure before checkpoint commit: rollback state and
  checkpoint breadcrumb, return the existing tool error path, emit no success receipt.
- Lost connection after commit: retain persisted state; the next resume is
  authoritative, while the interrupted agent must not claim acknowledgement.
- Missing checkpoint: successful recovery response with explicit absence,
  not a worker or storage error.
- Unavailable mmhmem: guidance warns that recent work was not saved and
  continues without invented memory or a claimed successful save.

## Testing Strategy

1. Service tests verify `Some`/`None` timestamps, database-row timestamp
   fidelity, existing breadcrumb history without a checkpoint, and rollback
   of a replacement when breadcrumb insertion or audit writing fails. Seed
   an earlier checkpoint and assert its content and timestamp remain intact.
2. Formatter tests cover all three states, timestamp ties, checkpoint-event
   labeling, missing history, and a new task ID that is not described as saved.
3. HTTP tests in `tests/handoff.rs` verify the public text contract, no hidden
   breadcrumbs, redaction and exact project isolation without a configured worker.
4. Stdio/multiprocess tests checkpoint A, record newer activity without saving
   state B, disconnect the client, and resume A through another process. Do
   not rely on timing a Ctrl+C during a database commit; use deterministic
   service failure injection for that boundary and process termination for
   transport recovery. Retain worker-notice tests.
5. Guidance checks review initial-task, four milestones, changed/unchanged
   final response, agent-controlled clear, direct Ctrl+C, failed-save and
   history-only scenarios against all shipped instructions. Mechanical
   checks enforce required semantics, token budget and package parity;
   the review record must distinguish these from live agent-compliance evidence.
6. Run native `cargo test` and strict clippy, then canonical
   `scripts/dagger-ci.ps1 -Call distribution` for package/guidance checks.
   Existing LOC, audit, isolation and size-cap gates remain mandatory.

## Rollout

Ship the Rust response changes in a binary release and refresh installed
skills/commands using existing installers. New guidance works with old
binaries but cannot expose timestamps or history their responses omit;
full feature verification requires the new binary. No store migration or
service configuration change is required. Existing running agents load new
instructions/binaries according to their normal restart/reconnect lifecycle.
