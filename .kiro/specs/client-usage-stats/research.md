# Research: client-usage-stats

Code read on 2026-11-03 at commit fe3313b. Findings are from reading the
source and tests; no stats command was run against a live store.

## Write path

- `src/mcp/tools.rs` `resume_or_handoff`: only when
  `updated_working_state_md` is present (a checkpoint) and `client_usage` is
  supplied does the server call `StatsCollector::record_client_usage`. A plain
  resume never writes stats. A stats failure is logged and does not fail the
  checkpoint.
- `src/services/stats.rs` `record_client_usage`: inserts a `token_stats` row
  with `kind = client_reported`, `avoided_input_tokens_est = 0`,
  `avoided_output_tokens_est = 0`, no worker tokens, and
  `details = {"prompt_tokens", "completion_tokens", "source", "label": "client_reported"}`.
  It also writes a `TOKEN_STATS_CLIENT` audit event with the same details.
- Rows are append-only. Nothing updates or deletes `token_stats` rows.
- Other writers: shunt delegated reads and cache hits, and
  `boilerplate_write`, all through `record_estimate`, with estimated avoided
  tokens in the numeric columns.

## Read path

- `src/cli/stats.rs` `AGGREGATE_SQL` groups by UTC day, project and harness.
  It sums `avoided_input_tokens_est` for non-client kinds as the estimate
  column, and the same column for `kind = client_reported` as the
  "AVOIDED (CLIENT-REPORTED)" column. The JSON field is
  `avoided_input_tokens_client_reported`.
- Server-written client rows therefore always contribute 0.
- `src/cli/stats.rs` unit tests and `tests/stats_cli.rs` seed a
  client-reported row with 700 in `avoided_input_tokens_est`, a shape the
  server never writes.
- The store is opened read-only for `mmhmem stats` (local-mode Req 8.6).

## E2E writer

- `tests/e2e/mod.rs` `checkpoint` sends one `client_usage` per task and mode,
  each under its own `workspace_task_id` and a distinct `source`
  (`opencode-e2e:<mode>:<task>`). Each report is that task's measured total,
  so latest-per-task-and-source counting gives the same result as summing.

## Implications

- The fix can be read-side only: the needed values already sit in `details`
  for every historical client row.
- Bundled SQLite (rusqlite `bundled`) includes the JSON functions, so reading
  `details` in SQL is possible. Whether to read in SQL or in Rust is a design
  choice.
- Changing the JSON field names is a data-contract change of local-mode
  Req 8.4. The old field never carried a non-zero value from server-written
  rows.

## Design discovery (light, extension of the stats CLI)

Consulted: `kiro-spec-design` skill with its light discovery, synthesis and
review-gate rules; steering `tech.md`, `structure.md`, `dev-environment.md`.

### Integration points found

- `token_stats` has `id INTEGER PRIMARY KEY AUTOINCREMENT`, so insertion
  order breaks ties between reports with the same millisecond timestamp.
- `src/cli/mod.rs` opens the store with `Db::open_read_only`, then calls
  `stats::aggregate`, `render_table` and `render_json`. The read-only
  opening stays as it is.
- `src/cli/stats.rs` is 407 lines including its tests. The size cap in
  `tests/loc_caps.rs` is 500 lines per `src/` file and 80 lines per
  function, so the client-usage logic needs its own module.
- `deploy/skills/unified-memory/SKILL.md` is at an estimated 174 of 200
  tokens (`check-routing-guidance.py`, `check-marketplace.py`), and
  `plugins/unified-memory/skills/unified-memory/SKILL.md` must stay
  byte-identical to it (regenerated by the marketplace build script).
- `StatsCollector::record_client_usage` is reachable from integration tests
  through the library crate, so tests can write rows through the production
  path. It stamps the current time, so tests that need a day boundary must
  adjust `ts_epoch_ms` after writing.

### Synthesis

- **Generalization:** latest-per-key counting, missing-value handling and
  source listing are one concern: turning client rows into per-day totals.
  One function owns it.
- **Build vs adopt:** read client rows with plain SQL and parse `details`
  with `serde_json` in Rust. SQLite's JSON functions would work in bundled
  SQLite, but `json_extract` raises an error on malformed JSON, which would
  fail the whole command for one bad row. Rust parsing degrades per row.
- **Simplification:** no schema change, no new columns, no write-path
  change. The estimate query loses only its client-reported sum.
